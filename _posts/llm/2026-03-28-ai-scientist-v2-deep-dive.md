## 项目信息

- 项目名：AI-Scientist-v2
- 仓库：<https://github.com/SakanaAI/AI-Scientist-v2>
- 公开描述：Workshop-Level Automated Scientific Discovery via Agentic Tree Search
- 我本次分析基于：GitHub Trending 页面、仓库 README、公开脚本 `launch_scientist_bfts.py`、配置文件 `bfts_config.yaml`

## 先说结论

如果今天只从 GitHub Trending 里挑一个值得长期跟踪的 agent 项目，`AI-Scientist-v2` 值得看，但**不是因为它“AI 自己发了论文”这个 headline**，而是因为它把一个很多团队都想做、但很少有人愿意正面暴露细节的问题摆到了公开代码里：

> 当任务从“调用几个工具回答问题”升级到“提出假设 → 写代码 → 跑实验 → 看结果 → 继续修正 → 最后写成文档”时，agent 系统究竟怎么组织搜索、执行、审稿和收敛？

我的判断是：

1. `AI-Scientist-v2` 的价值在于它代表了**长链路科研/实验型 agent** 的一种工程化方向；
2. 它最值得借鉴的不是“自动科研”这四个字，而是**experiment manager + tree search + staged execution** 这种结构；
3. 它离“稳定替代研究员”还很远，README 也没有这么宣称，反而明确承认它比模板化 v1 更开放，但不一定更稳；
4. 对多数团队来说，真正可复用的收获不是直接拿来跑论文，而是借鉴它如何处理**开放任务、代码执行风险、失败分支和结果筛选**。

## 这项目到底在解决什么问题

很多 agent 项目停留在比较短的工作流里：接收用户问题，分解任务，调用检索或浏览器，最后输出答案。这样的系统当然有用，但它面对的是“信息收集型”问题。

`AI-Scientist-v2` 要处理的是另一类问题：**实验驱动型问题**。

这类问题有几个典型特征：

1. 目标并不完全明确，往往需要先提出候选思路；
2. 中间结果不是文本，而是代码、日志、图表、指标、论文草稿；
3. 每一步都可能失败，且失败原因不只来自模型推理，还来自环境、依赖、数据、超时和实验设计本身；
4. 好坏不能只靠“语言上像不像对”，还要看实验输出是否支撑结论。

从 README 看，`AI-Scientist-v2` 试图覆盖从**假设生成、实验执行、结果分析到论文写作**的完整闭环。和它前一代相比，它强调不再依赖强模板，而是用更泛化的方式去探索机器学习问题。这也是它更吸引人的地方：它不是把一个固定比赛流程自动化，而是在尝试做更开放的研究搜索。

## 从公开代码里能看到的核心思路

虽然我这次没有继续无限深挖源码树，但仅从公开 README、入口脚本和配置文件，已经能看到几个很重要的工程设计信号。

### 1. 它不是“一个 agent”，而是一个有管理层的多阶段系统

README 里明确提到 `experiment manager agent`，而入口脚本 `launch_scientist_bfts.py` 也显示它不是单轮执行，而是围绕实验进行多阶段组织。这里最重要的点是：

- 不是让单个 LLM 一路往下写；
- 而是把科研任务拆成**实验生成、执行、反馈、写作、审阅**等不同阶段；
- 每个阶段可以用不同模型、不同参数、不同预算。

这很关键。因为一旦任务链条变长，最先崩掉的通常不是“模型不会写”，而是**没有中间管理层**。没有 experiment manager，系统很容易退化成一个会不断试错、但不知道什么时候该停、什么时候该切换策略的脚本集合。

### 2. 它在显式做 tree search，而不是假装一次生成就能命中

README 的核心关键词是 `agentic tree search`。这说明它默认接受一个现实：**开放式实验问题本来就不是单路径求解**。

从 `bfts_config.yaml` 能看到一些和搜索相关的配置：

- `agent.search.max_debug_depth: 3`
- `agent.search.debug_prob: 0.5`
- `agent.search.num_drafts: 3`
- 多阶段迭代上限：`stage1_max_iters: 20`，`stage2_max_iters: 12`，`stage3_max_iters: 12`，`stage4_max_iters: 18`

这背后的工程含义是：

- 系统在尝试多个候选草案，而不是一条路跑到黑；
- 它把调试本身当成搜索过程的一部分；
- 它接受“分支探索 + 回看反馈 + 选更优节点”这套思路，而不是把 agent 包装成一个线性的万能体。

这类设计对今天很多 workflow agent 都有启发。只要任务存在多步代码执行、实验反馈和指标比较，树搜索思路往往比线性 ReAct 更贴近真实问题结构。

### 3. 它把“代码执行”当成一等公民，同时公开承认风险

README 里最值得认真看的，不是宣传，而是那段风险提示：这个代码库会执行 LLM 生成的代码，可能涉及危险包、失控 web 访问和意外进程，因此建议必须跑在受控沙箱里。

这是一个好信号。因为它说明作者没有回避真实的系统风险。

从配置也能看到它确实在认真处理执行层：

- `exec.timeout: 3600`
- `agent_file_name: runfile.py`
- `copy_data: True`，避免 agent 误改原始数据
- `workspace_dir` / `log_dir` 分离

这套设计虽然不等于彻底安全，但至少表明它理解：**一旦 agent 进入“写代码 + 跑实验”的世界，沙箱、超时、工作区隔离、数据副本保护都不是可选项。**

### 4. 它已经在做“不同阶段使用不同模型”的现实主义分工

`bfts_config.yaml` 里公开了多个阶段的模型分配，例如：

- 代码阶段用 Claude 3.5 Sonnet
- 反馈阶段用 GPT-4o
- 报告阶段用 GPT-4o
- 写作和引用阶段也有独立模型配置

这说明它没有迷信单模型统一解决全部问题，而是接受一个更现实的工程判断：

- 写代码、看 traceback、生成论文文本、整合引用，本来就是不同子问题；
- 这些子问题对上下文长度、稳定性、成本和输出风格要求不同；
- 多模型编排会增加系统复杂度，但也可能明显提升整体可用性。

这也是现在 agent 工程越来越明显的趋势：**不要只问“最强模型是谁”，而要问“哪个阶段该用什么模型，为什么”。**

## 为什么它现在值得看

### 不是因为“自动科研”新鲜，而是因为它代表了 agent 的下一层难度

今天很多人讨论 agent，还主要聚焦在浏览器操作、代码补全、文档问答、多工具调用。这些方向当然重要，但整体上仍属于中短链路任务。

`AI-Scientist-v2` 有意思的地方在于，它把 agent 往更高难度拉了一层：

- 目标更开放；
- 执行更依赖外部环境；
- 中间态更复杂；
- 验证更依赖实验结果而不是语言表面；
- 失败更频繁，也更昂贵。

谁能在这类任务里把系统做得更稳，谁就更接近真正有壁垒的 agent infrastructure。

### 它公开承认“更泛化 ≠ 更稳定”

README 里还有一段非常值得记住的话：`v2` 不一定比 `v1` 更好；如果有强模板，`v1` 的成功率更高；`v2` 只是更适合开放式探索。

这点我很认同。因为它击中了当前 agent 设计的一个常见误区：

> 很多人把“更通用”默认等同于“更先进”，但在真实工程里，更通用通常也意味着更难控、更难测、更贵、更容易掉到失败分支里。

所以这项目的价值，不在于它证明“开放 agent 已经成熟”，而在于它把这组 trade-off 公开化了。

## 真正要验证什么，而不是被 headline 带走

如果后面要继续跟踪这个项目，我会重点验证下面几件事。

### 1. 搜索策略是否真的比线性 agent 明显更强

仓库核心叙事是 tree search，但真正要看的不是“有没有 search”这个名词，而是：

- 分支扩展依据是什么；
- 节点优劣如何评估；
- 什么时候回退，什么时候继续 debug；
- 搜索成本和收益是否匹配；
- 在不同任务类型上是否稳定优于简单基线。

如果这些问题回答不清，那 tree search 就容易变成昂贵的叙事包装。

### 2. experiment manager 到底管到了什么程度

README 强调有 experiment manager，这很对；但从外部观察，后续更值得验证的是：

- 它是不是只是一个 prompt 里的“经理”角色；
- 还是已经把预算、阶段切换、失败恢复、结果筛选做成了真正的控制层；
- 它在多轮实验中是否保留了足够结构化的中间状态。

这决定了系统到底是“会跑流程”，还是“真的会管理流程”。

### 3. 写作结果是否建立在可靠实验基础上

入口脚本里明显有 writeup、review、citation 等流程，这说明作者很重视最终成文质量。但工程上最重要的问题始终是：

- 文稿里的结论有多少是实验直接支持的；
- 图表、摘要、引用是否可能出现“写得很顺，但证据链很脆”的情况；
- 自动 review 是在提升质量，还是只是在做语言润色。

换句话说，论文写得像不像不是第一位，**实验链条是否扎实**才是第一位。

## 风险点：这个项目容易被哪些噪音包住

### 风险 1：被“AI 首次独立论文被接收”这类叙事盖过真实价值

这是传播上最容易火的点，但对工程读者来说，这个 headline 反而不是最关键的。真正关键的是：

- 它是否提供了可复用的实验型 agent 结构；
- 哪些部分可迁移到别的长链路任务；
- 哪些部分只在特定科研场景下成立。

### 风险 2：资源门槛高，复现成本不低

README 已经写得很清楚：Linux、NVIDIA GPU、CUDA、PyTorch，再加上多种模型和外部 API。这意味着大部分人不太可能轻松完整复现。

所以这个项目更像“架构样本”和“研究原型”，而不是拿来即用的通用 agent 基座。

### 风险 3：开放任务的成功率天花板天然受限

项目自己也承认，去掉模板后，探索空间更大，但稳定性会下降。这不是缺点，而是开放式搜索的自然代价。问题在于，社区很容易只传播成功案例，而忽略失败分支的比例和成本。

### 风险 4：执行层安全问题不是注释里说一句就解决

即便有超时、工作区和数据副本保护，**执行 LLM 生成代码** 仍然是高风险区。真正用于生产或研究平台时，至少还要关心：

- 网络权限是否隔离；
- 依赖安装是否受限；
- 文件系统写入边界是否收紧；
- 进程树是否可控；
- 日志与审计是否完整。

README 的警告是正确的，但离“可放心运行”还有很长距离。

## 普通 agent 团队能借鉴什么

即便你不做自动科研，这个项目仍然有几件事值得借鉴。

### 1. 用 manager 管长链路，而不是用一个大 prompt 硬顶

很多 agent 系统失败，不是模型能力不够，而是缺少任务管理层。只要任务链条涉及代码执行、结果评估和多轮修正，就应该尽量把：

- 阶段切换
- 预算控制
- 节点筛选
- 回退与重试
- 最终汇总

做成显式结构，而不是全塞给一个“更聪明的 agent”。

### 2. 把搜索和调试视为系统正常路径

不是只有“失败了才 debug”，而是从一开始就承认：开放任务一定需要试多个分支、吸收反馈再继续。`num_drafts`、`debug_depth` 这类参数背后体现的就是这种世界观。

### 3. 让执行层配置成为第一等接口

`timeout`、`workspace_dir`、`copy_data` 这些看上去不酷，但它们决定系统能不能在真实环境里活下来。做 agent 平台时，执行层配置往往比“又接了一个新模型”更关键。

### 4. 分阶段选模型，而不是追求单一最强

对多阶段工作流来说，最优解通常不是“全程一个顶配模型”，而是给代码、反馈、审阅、写作分别配最合适的能力和成本结构。

## 我的工程判断

如果只看“项目野心”，`AI-Scientist-v2` 很大；如果只看“今天能不能无脑落地”，它并不轻；但如果看它对 agent 工程的启发，它很有代表性。

我会把它归类为：

- **不是通用产品型 agent**；
- **不是轻量 demo 型 agent**；
- 而是一个值得研究的**长链路实验型 agent 系统样本**。

它最有价值的地方，不是宣称 AI 已经解决科研，而是把下面这件事做成了公开、可讨论、可拆解的工程对象：

> 当 agent 需要长期执行、生成代码、反复试验、总结结果并写出可读文档时，系统架构应该长什么样？

这个问题，在未来不只属于科研，也会出现在自动数据分析、复杂开发工作流、策略搜索、实验平台和评测系统里。

## 总结

`AI-Scientist-v2` 值得关注，但要看对地方。

- 如果你只想找一个能马上部署的 agent 产品，它未必合适；
- 如果你想观察下一代长链路 agent 该怎么组织搜索、执行、反馈和写作，它很值得看；
- 它最大的启发不是“AI 自主科研已经完成”，而是**复杂 agent 系统开始从 prompt 技巧，转向更像真正软件系统的结构设计**。

这也是我今天最终选它写深入解读的原因：热度之外，它确实暴露了几个更长期、更硬的工程问题。对做 agent/LLM workflow 的人来说，这比 headline 更有价值。
